# 虚构示例：修复花园路灯

此例完全虚构，仅演示文档、配置、美术和音频如何关联。参数、资源ID与产品决定不是任何真实项目的默认规则。下面假设需求负责人已经在演示中选定所述方案；真实任务必须核自己的授权与证据。

## 策划片段

玩家靠近损坏路灯，点击“修复”。系统检查背包中的零件，满足条件时扣除3个零件，将路灯状态从 damaged 切到 repaired，并播放修复表现；不足时只提示差额。退出重进读取 repaired 状态，不再次扣费。

这里“3”来自演示配置参数 cost；“修复只能结算一次”为演示机制。扣费与状态如何在实际客户端／服务端实现，由具体项目另行确定，视频不能证明后台原子操作。

UI状态：可修复、零件不足、修复中、已修复。修复中拒绝重复触发；返回后显示当前真实状态。正式游戏是否允许中途取消仍须产品决定。

## 配置映射

| 中文说明 | 配置ID | 需要零件数 | 完成状态 |
|---|---|---|---|
| 类型（演示） | string | int | string |
| 英文字段 | id | cost | target_state |
| 数据（演示） | garden_lamp_repair | 3 | repaired |

正式工作簿把各列依次放入中文说明、类型、字段三个表头行，再放数据；示例表仅为方便阅读。

## 美术拆分

| 需求编号 | 内容 | 数量口径 | 新制／复用 | 验收 |
|---|---|---|---|---|
| ART-DEMO-001 | 路灯损坏与修复两状态 | 一套路灯，两个状态；文件数待实现确认 | 演示假设新制 | 两状态轮廓一致，亮灯部位明确 |
| ART-DEMO-002 | 修复火花 | 一组特效 | 演示假设新制 | 开始／结束时点对应修复表现 |
| ART-DEMO-003 | 修复按钮 | 一个组件，四个适用状态 | 是否复用待确认 | 状态与操作限制一致 |

资源目录中其它场景引用 ART-DEMO-001 时指向主条目，不再新增一套路灯数量。美术表完成时制作状态仍为“需求已整理”，不会变成“资源已入端”。

## 音频片段

“修复完成提示”：状态实际变成 repaired 时播放一次；不循环；重进和重复点击不补播；演示未指定音频资产，复用待确认。程序 Event、WWISE事件、对接人和合入时间都留空。

如果音效方案改为“施工循环”，必须一起补开始、停止、退出时清理与并发去重，不能只把名称改掉。

## 本例的检查

- 同一条修复规则在文档、配置、状态和声音中一致。
- 当前未知项明确留空，没有编成已确认后台机制。
- 资源需求数量、状态数与最终文件数没有混算。
- 假设用户下一轮删去火花，当前稿及目录同步取消，旧例子不自动恢复它。
- 若想把“所有修复都花3个零件”变成长期规则，需另行提案确认；本例不能提供这种授权。

# 游戏策划与资源交接

先确定本次要交付的项目、当前来源、范围和验收。只读取相关专题，不因本 Skill 覆盖多类产物就自动生成全部文档。

## 路由

| 请求 | 读取 |
|---|---|
| 接单、视频拆解、需求不完整 | [需求与证据](references/01-intake.md) |
| 策划案、系统案、局部改稿 | [策划文档](references/02-design.md) |

## 共用约束

- 当前用户指定原件优先，确认作者源后再写。无权威来源时只做可审查草案；不凭文件最新日期或最大版本号选稿。
- 原件只读保留、修改另存。沿实际依赖同步文档、配置、UI、资源和验收，保留用户手改及删除。
- 小改用最小充分流程。角色是需要覆盖的职责，不等于必须创建多个代理；有明确授权时才委派。同一文件维持明确写入归属。
- 文档／配表修订默认新增和修改标黄；语义颜色、原编号和原表结构另行保留。默认文档版本 1.0，不自动递增；作者由使用者提供，制作起止日期为当日。当前项目规则优先。
- 每次新增、修改、删除永久策划规则或扩大其范围，先展示原文、拟改、理由、范围和影响，取得本次明确确认。普通已授权文稿修订继续执行，记录案例不等于规则生效。
- 只使用当前环境实际可用的工具和 Skill；本包不附带文表渲染器、图片生成或音频服务。能力缺失时注明未验证项，继续独立可做的工作。
- 索引不替代原件，哈希不替代语义验收，文件存在不等于完成，助手交付不等于用户接受。
